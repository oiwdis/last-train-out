## Sampler investigation

The exact message was `WARNING: Metal does not support LOD bias for samplers.` A lone camera with no mesh, light, texture or game material triggered it as soon as its viewport scale changed from 1.0 to 0.65. At Low and Medium, Godot adds `log2(min(scale, 1.0))` to the viewport bias and allocates viewport-wide mipmapped samplers. Both ordinary mipmap and anisotropic filter choices receive the bias. The Metal backend ignores the unsupported bias when constructing its native sampler. The global warning occurs once per process. There is no warning counter per shader or per frame. [Viewport calculation](https://github.com/godotengine/godot/blob/4.5.1-stable/servers/rendering/renderer_viewport.cpp#L265) · [Mipmap filter allocation](https://github.com/godotengine/godot/blob/4.5.1-stable/servers/rendering/renderer_rd/storage_rd/material_storage.cpp#L2444) · [Metal sampler creation](https://github.com/godotengine/godot/blob/4.5.1-stable/drivers/metal/rendering_device_driver_metal.mm#L770)

The first project-only experiment temporarily deallocated the render target and applied both viewport settings before drawing. It still warned on the first scaled, camera-only frame. At scale 0.6499999761581421, the needed correction is approximately 0.621488429664. The viewport stores 0.621488451958. Godot evaluates the mixed-precision sum before converting its nonzero residual to a float. All six textured test images matched the unmodified Metal output byte for byte. The experimental code was removed. The failed job, original log and images remain available. [Public setter experiment](validation/milestone354/baseline/public-setter-probe.zip) · [Failed job log](validation/milestone354/baseline/public-setter-job.log) · [Godot minimum helper](https://github.com/godotengine/godot/blob/4.5.1-stable/core/typedefs.h#L128)

The template now requests a neutral sampler bias at the viewport allocation site on Metal. It leaves filtering, anisotropy, render scale, shadows, textures and MSAA intact. Explicit unsupported RenderingDevice requests still reach the driver warning. The regression runs the stock viewport, the corrected viewport, and an explicitly invalid sampler in separate processes. It checks the actual driver, all severity messages, and hashes the decoded pixel bytes at six scales and transitions. A sampler warning does not identify a GPU timeout, memory shortage or frame outlier. [Single engine patch](../tools/macos/engine/viewport-metal-sampler.patch) · [Control fixture](../tools/macos/metal_sampler_probe.gd)

In the packaged control the stock executable warned once at scaled viewport allocation. The patch produced zero warnings across all six draws, including returning to the original scale. A deliberately invalid direct device sampler produced the original warning in the patched executable. All 18 pixel hashes matched their corresponding control frames. The scanner therefore still detects an unsupported request. [Three-process logs, hashes and 18 PNGs](validation/milestone354/raw/metal-sampler.zip)

In 4.5.1 the native Metal driver returns false from its pipeline-cache creation entry point. The macOS backend also has two library-loading policies. Its default starts asynchronous compilation with `newLibraryWithSource:options:completionHandler:` as shaders arrive. With `GODOT_MTL_SHADER_LOAD_STRATEGY=lazy` it creates the Metal library synchronously on first use. Both policies still create render and compute pipelines. The explicit Metal selector defaults to first use and honors a caller-specified policy. The controlled comparison swaps the order of both policies on two independently provisioned hosts running the original pack. The candidate also times both policies through every location. A separate traced process collects Apple log signposts from Godot’s shader and pipeline creation entry points. Shader timings overlap and cannot be added together to obtain elapsed startup.
